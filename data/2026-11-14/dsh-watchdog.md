## 新增插件 **`@local/watchdog`**（工作区 `…

新增插件 **`@local/watchdog`**（工作区 `dsh_plugins\watchdog\`，独立 git 仓库，row id `watchdog` / entry `include:watchdog`，`install_bundle` 以本地目录装入 desktop profile，`application: applied`）。功能：监听系统文件变化，并以一次内容变化**结束工具等待**或**拉起一轮回复**。两个工具：`listen_file`（必填 `path` + `description`；`wait:true` 默认**阻塞**到变化/超时/被别的插件结束，返回 `changed` 与前后签名；`wait:false` 立即返回资源 ID，之后每次变化由插件**推消息**进会话）与 `unlisten`（结束等待、停监视器、删持久化记录；只能关本会话的监听）。判变化用**内容哈希**（sha256），文件事件只当作「去重读一次」的信号；超过 `maxHashBytes`（默认 8 MiB）或读不出来时退回提供者的 `version`（结果里标 `scheme`）。服务 `ctx.watchdog`：`list/get/cancel/cancelAll/endWait/on('change')`，`endWait` 只结束等待、不关监听。**关键实测坑**：`ctx.fs.watch(file)` 由 fs-local 自己算锚点（`dirname(file)`），该目录还不存在时锚点高一层，而 chokidar 用 `depth: 0`，于是**显示已监听却永不触发**；插件因此自己选锚点（目标是目录就观察自身，否则锚到最近一层已存在的目录），并在文件自己的目录出现后自动下移（`maybeReanchor`），重复 `listen_file` 时也先修正锚点、不等事件。持久化：**按会话一个 JSON**（`$DSH_HOME/plugin-data/watchdog/sessions/<sessionId>.json`，可用 `stateDir` 改），原子写（tmp+rename）、按会话合并写、监听清空即删文件；插件卸载**只停监视器不删记录**，下次激活或启动时比对哈希，把「DSH 没运行时发生的变化」变成 push 通知（会话没有活 Agent 时**排队**，等 `agent/created` 再投递）或下一次 `listen_file` 的 `changed:true`。装了 `backend-resource` 时每个监听是一个可关闭的后台资源（可选依赖，走 `ctx.inject(['backendResources'])`；从面板关闭与 `unlisten` 走同一条 closeListen 路径，所以 requestClose 必须按 record.closed 而不是按「这次调用有没有真的关掉」回报，否则会误报 closed:false）；**不需要 `lib-cache`**（纯 node:crypto + node:fs，无第三方库）。测试 30 项全绿：`node --test-isolation=none --test "tests/*.test.mjs"`（沙箱内裸 `node --test` 会 spawn 子进程失败）。已实测：等待中的文件被改写 → 2.2 s 结束；**父目录当时不存在**的嵌套文件 → 18.4 s 结束（修复前此场景永不触发）；已存在文件的后续编辑 → 17.2 s 结束；push 模式改动确实作为消息送达本会话；停用再启用后 restore 把离线变化比对出来（记录从 a2dc983f 前进到 dff1faf5，三个监听全部重挂）。**改本地插件源码后 HMR 不重载模块，必须 `restart_dsh`**；已提交「渲染文本补资源 ID」的修复，当前进程尚未加载，下次启动生效。 **空闲唤醒已实测**（2026-11-14 13:06:38）：子代理充当外部写入者，先静默 90 s 再写文件、写完继续睡 480 s；本会话在**空闲**状态下自己起了一轮并收到 `watchdog_change`（哈希 add1aeff…），证明 `agent.followup()` 对空闲会话确实能起一轮——当时子代理还在睡，完成通知不可能触发。另注：`Start-Process` 起的脱离进程会被 DSH 的作业对象随工具调用一起收掉，**不能**当作跨轮外部写入者；要跨越回合做外部动作，用受管后台任务或子代理。 **插话（steer）已实测**（2026-11-14 13:08:51 与 13:09:16）：push 监听默认 `delivery: steer`，收到变化时若 Agent 正在跑，就用 `agent.steer()` 把通知**插进当前这一轮的下一步边界**，不用等回合结束（实测两条通知都落在同一个未结束的回合内，模型当场就能看到并处理）；Agent 空闲时用 `followup()` 起一轮；`steer` 被拒（回合已关）自动退回 `followup`，不丢通知；启动比对出的离线变化一律 `queue`（旧闻不该打断刚有进展的工作）。注意：文件的「创建」与「修改」算两次变化，会各发一条通知（250 ms 内才合并），写入密集的外部进程可适当调大 `debounceMs`。
