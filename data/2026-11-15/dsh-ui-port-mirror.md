**依赖核查（用户问「是不是依赖了其它的插件」，要求一起打包）**：没有可一起打包的插件 —— Host 侧只 `inject: ['webServer']`，`connection.authenticatedUrl` 按 `ctx.get('connection')` 惰性读、故意不注入；Client 侧 `inject: ['slots','locale']` + `dsh.client.inject: ['@deepseek-ai/dsh-client-ui-settings']`，注册槽位 `settings.section` / `sidebar.footer.action` / `shell.overlay`；React 来自宿主模块表，证书用 Node 内置 crypto，vendored 只剩 qrcode/jsqr/sha256/presence/tunnel-crypt。这些全部随 DSH 安装按名字解析，打进 tgz 也无人使用，所以「一起打包」的正确做法是把依赖面写清：README 加「依赖」表、SKILL.md 加「Dependencies」表（逐项写缺失时的失效方式 + 版本核对），并明确「不要靠拷包或再装插件来满足」。**没加 `engines.dsh`**：管理器会按它拦安装，但范围语义与 rc 版本比较没实测，宁可文档化。重打后产物：tgz 121,470 B sha256 `818c44aab125c364e01ebe9aa1901e0850bd703044ee2ce07f18cc7f061132a4`、zip 130,242 B sha256 `7a0aa02beb86047fd99a408a61e81c253fe71fd236cdbc6fb63b4ef76f649406`，提交 `d341660`。**活证据**：`Slots.listSubTree` 里 `sidebar.footer.action` 的 occupant `ui-port-mirror`(order 10) 与 `settings.section` 的 `ui-port-mirror`(order 17) 都 active，槽位 declaredBy 分别是 sidebar / sidebar.settings 的 WC 条目。

**lib-cache 从未用于本插件（用户追问「是不是从来没用过」）**：工作区里 grep 不到 `libCache`/`lib-cache` 任何引用，git 全历史也没有引入或移除它的提交。三个第三方库是 2026-11-10 做局域网票据扫码时进的包（`vendor/qrcode.cjs`、`vendor/sha256.js`、`vendor/jsqr.js`，见 20261110-005、20261110-007）；当时 lib-cache（2026-10-30 建）已存在，但结构上不适用：jsQR 与 js-sha256 必须由镜像自己的壳页当 classic script 加载（Host `readFileSync('./vendor/*')` 后经 `/__mirror/assets/*` 吐字节），LAN 设备到不了宿主 loopback 的 `/lib-cache/...`、跨源也过不了栅栏；qrcode 走 `ctx.libCache.import` 会变成「首次使用需联网 + 必需 inject libCache」，离线局域网直接坏，还让可分发插件依赖另一个可选插件。结论：lib-cache 对它的合理角色只是 vendor 文件的**来源/升级渠道**（取官方单文件构建、核 sha256 后覆盖 vendor），不是运行时依赖。
