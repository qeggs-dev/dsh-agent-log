## 新插件「打断等待」

（`D:\Projects\Deepseek_Harness_Workspace\dsh-job-wait`，包 `@local/dsh-job-wait` v1.0.0，desktop profile bundle，行 id `job-wait` / entry `include:job-wait`，`install_bundle` → `application: applied`、`warnings: []`；无 Config、无 Agent 工具，只有 Host 侧一段包装 + 一个 UI 按钮）：用户要求「让用户能手动打断后台任务的等待，并保持后台任务继续运行」。**为什么需要它**：`job_output(wait:true)` 调 `ctx.jobs.wait(id, timeoutMs, caller, exec.signal)`，只有「任务结束」和「等满超时」两个出口；按 GUI 的停止键会中断整个 turn（任务虽活着，这一轮的工作作废）。**实现（唯一可行的接缝）**：`ctx.jobs` 是 `LocalJobRegistry` 的普通实例（`extends JobRegistry`，不是 cordis Service），插件在 `apply` 里**直接替换实例方法 `jobs.wait`**（记下原型原值、用 `Object.hasOwn` 判断、卸载时 `delete` 还原），每次调用另挂一个本插件自有的 `AbortController` 并与调用方 signal 用 `AbortSignal.any` 合并；被打断时包装层**吞掉 `"wait aborted"` 拒绝**、改为返回 `jobs.get(id, caller)`——与超时返回的是同一个 `JobView`，所以工具调用**正常收尾**（走 `readBody(jobs.read(...))`），模型带着已有输出继续下一步，任务完全不受影响。**端到端实测**：子会话起 90s 后台任务 → `job_output(wait:true, timeout_ms:600000)` → 从插件外面 `POST /job-wait/cancel` → 等待在 **8.37s** 返回（不是 600s），内容是 `(no new output)` + `[status: running]`，紧接着 `job_list` 仍是 `running`，无任何 timeout/cancel 错误。**UI**：slot `conversation.input.left`（id `job-wait`、order 30，排在 `continue-task` 之后），**只在存在等待时渲染**（每 1.2s `GET /job-wait/state?session=<id>`，无等待则返回 null），点击 `POST /job-wait/cancel`（请求头 `x-dsh-job-wait: <token>`，token 由 state 响应带回），两条路由都校验 Origin（`dsh-app://app` 也算同源）。**服务接口**：`ctx.jobWaitControl.active() / cancel({id|jobId|sessionId|all}, reason)`，形状对齐 `sleepControl`（被打断的等待正常返回，不是失败）。**两条运行时事实**：①`jobs.wait` 的 `caller` 实参是 **`exec.agent.id`**（不是 session 对象），按 sessionId 取消即按 agent.id 过滤；②`install_bundle` 之后客户端半**当场就进了 boot graph**（client Slots inspect 里 `conversation.input.left` 立刻出现 `job-wait`、`active: true`），不需要重启 App。**已知边界**：插件挂载前已经在等的 `job_output` 打不断（等它自己超时）；`jobs` 服务被替换后包装随旧实例消失（重载本插件即恢复）；只影响 `jobs.wait`，不影响 `job_kill`。**未验证**：按钮的视觉观感与真实点击（无浏览器控制）。
